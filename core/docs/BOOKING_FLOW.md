# Как устроена система бронирования (core)

> Кратко: **кто может что и когда** (user / service / master_services / work_schedules) → **расчёт свободного времени** (slots, на лету) → **факт записи** (bookings с конкретным временем). Слоты **не хранятся** в БД — они вычисляются из графика, услуги и уже существующих броней.

## Таблицы и роли

| Таблица | Роль |
|---|---|
| `user` | аккаунты: клиенты, мастера (`role=groomer`), менеджеры |
| `service` | услуга: длительность + буферы до/после, цена |
| `master_services` | M2M: какие мастера (`user`) оказывают какие услуги |
| `work_schedules` | регулярный график мастера: день недели + начало/конец + выходной |
| `bookings` | факт записи: `master_id` + `service_id` + `start_time`/`end_time` + клиент + `pet_id` + `comment/options` |
| `booking_settings` | singleton-настройки: шаг сетки слотов (`slot_interval_minutes`, задаёт админ) |
| `pet` | питомцы клиента (`owner_id` → `user`) |

> Таблицы `slots` больше нет: слоты — расчётная величина.

## Цепочка данных

```
user (мастер, role=groomer) ── master_services ── service (duration + buffers)
        │
  work_schedules
        │  расчёт на лету (slot_generator)
        ▼
   slots (в ответе API) ── booking (конкретное время)
                              │
                       client (user) / contact + pet
```

## Поток записи

1. **Настройка:** мастер (`user.role=groomer`) ↔ услуги (`master_services`), график (`work_schedules`), у услуги — `duration` + буферы. Админ задаёт шаг сетки: `POST /slots/interval {interval_minutes}`.
2. **Выбор:** клиент / фронт / интеграция выбирает услугу, дату, при желании мастера.
3. **Доступность:** `POST /slots/available {service_id, master_id?, date_from, date_to?, pet_id?}` — для каждого дня строим сетку стартов с шагом `interval_minutes` по графику мастера; кандидат валиден, если его footprint (`start − buffer_before … end + buffer_after`) помещается в рабочее окно и не пересекается с footprint'ами активных броней. Ответ — список слотов `{master_id, service_id, start_time, end_time, available}`.
   - Если `master_id` не задан — мастера на день выбирает функция `select_master_for_day` (приоритет: у кого уже есть запись в этот день, затем больше записей, затем больше свободных слотов; легко переписать).
4. **Бронь:** `POST /bookings {master_id, service_id, start_time, client_id | client_name+client_phone, pet_id?, options?}` — валидируются график, сетка, пересечения; под advisory-lock по мастеру вставляется бронь с конкретными `start_time`/`end_time`.
5. **Отмена:** booking → `cancelled`, время снова участвует в расчёте доступности.

## Почему так

- Слоты не материализуются: нет «залипших» статусов, мусора и обязательной генерации; `GET` больше не пишет в БД.
- `booking` хранит конкретное время (`start_time`/`end_time`), поэтому время/мастер/услуга не «расцепляются».
- Один `booking` = одна услуга = один интервал. Несколько услуг/питомцев = несколько броней.
- Мастер — это `user` с `role=groomer`: календарь/график привязан к тому же аккаунту, что и права/авторизация. Отдельной таблицы `resources` нет.
- Клиент: `client_id` (авторизованный) **или** `client_name`/`client_phone` (гость/интеграция).
- `options` — произвольные доп. данные; `pet_id` — питомец клиента.
- Буферы услуг участвуют в расчёте доступности и проверке пересечений, но не «продаются» клиенту.

## Статусы

- `booking`: `pending` → `confirmed` → `completed`; в любой момент до завершения — `cancelled`.
  Активны (`pending`/`confirmed`) — учитываются при расчёте слотов и защите от пересечений.
  `completed` сохраняется в истории визитов питомца и продолжает занимать свой интервал;
  `cancelled` — единственный статус, при котором время снова доступно для новых броней.
