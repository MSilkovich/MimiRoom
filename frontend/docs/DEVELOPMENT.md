# Разработка и API

Запуск и команды описаны в [README](../README.md). `dist/app.js` — рабочая CRM, `client.js` — кабинет и мастер записи, `team-tools.js` — мастера/услуги/графики/профиль, `api.js` — адаптер API и сессия. `server/http.mjs` раздаёт статику и проксирует core. Сборщик не нужен; изменения видны после обновления страницы.

Контракт: [openapi.json](openapi.json). `/api/v0.0.1/bookings`, `POST slots/available`, статусы pending/confirmed/completed/cancelled. Идентификатор ответа booking_id адаптируется в book_id для внутренних компонентов. При создании передаётся точный ISO start_time из ответа slots, без повторного расчёта браузером. Отображение — Europe/Moscow.

BookingUpdate изменяет только метаданные/статус. Отмена и завершение используют специализированные POST endpoints. В случае 409 новая запись не создаётся автоматически: пользователь заново выбирает время.

Роль берётся из GET users/{id}; query-параметры и демо-переключатель не дают прав в live. Клиент читает pets из собственного профиля и только свои bookings, грумер — свои записи и графики. Авторизация на сервере остаётся обязательной. Менеджер не управляет ролями и не редактирует чужие учётные записи.

Для Telegram используется POST users/link/code?provider=telegram. Полученный deep_link открывается пользователем, код потребляет tg сервис. Не запускайте одновременно Telegram polling из optional frontend support server и штатного tg с одним bot token.

CORE_API_URL задаётся на Node-сервере и недоступен как пользовательский open proxy. Прокси сохраняет коды ошибок core, ограничивает размер тела, время ожидания и запрещает чужой Origin для изменений. Production deployment: HTTPS/reverse proxy, отдельная настройка допустимых host/origin (локальный сервер принимает localhost/127.0.0.1), секреты через окружение. Текущий сервер рассчитан на локальную разработку.
